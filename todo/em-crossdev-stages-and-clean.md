# `em crossdev`: partial stages (`--stage N`, `--ex-only`) and `-C/--clean`

Status: ✅ landed and live-verified 2026-11-25. Open: the two findings below. Two high rows of [[em-crossdev-parity]].
Consumer: crossdev-stages' em backend (`sandbox setup --em`), which today can only run
the whole `--setup` and has no way to drop a target.

## Decisions (Luca, 2026-11-24)

- `--stage N` (0–4), no `-sN` or `--stage0..4` aliases.
- `-C` removes everything, the sysroot included.
- Spelling: `em crossdev -T <tuple> -C` (`--clean`), a boolean.

## Real crossdev, for reference (read from `/usr/bin/crossdev` 20260623)

Stages are cumulative, `-s4` is the default:

| Stage | gcc model | LLVM model |
|---|---|---|
| 0 | binutils | clang-crossdev-wrappers (after checking LLVM_TARGETS) |
| 1 | gcc stage1 (headers first with `--with-headers`) | compiler-rt (same headers rule) |
| 2 | kernel headers | kernel headers |
| 3 | libc | libc |
| 4 | gcc stage2 | libunwind, libcxxabi, libcxx |

`--ex-only` skips 0–4 and runs only `--ex-gcc/--ex-gdb/--ex-pkg`; extras otherwise run after
any stage level. Every step is `emerge -u`, so a rerun skips what is installed.

`-C TARGET` refuses a host CHOST; removes the overlay category (and an autogenerated overlay
and repos.conf left empty); `package.{accept_keywords,env,mask,use}`,
`profile/package.use.{force,mask}` and `env/` entries for `cross-<T>`; the clang cross cfg;
`emerge --rage-clean cross-<T>/*`; the `<T>-*` binutils/gcc wrappers and
`env.d/{binutils,gcc}` configs; `<T>-emerge` & co; then `usr/lib/gcc{,-lib}/<T>` and
`usr/<T>`, prompting for a non-empty dir unless `-f`.

## em today

- `toolchain_plan` (`crossdev/stages.rs`) is one ordered `Vec<StageStep>`; em's order differs
  from crossdev (gcc-stage1 before the headers; LLVM puts headers before compiler-rt).
- `--setup` runs it all; `-r` skips leading steps the milestones (`crossdev/milestones.rs`,
  in the sysroot) still vouch for. Without `-r` the record is cleared and every step runs.
- `--init-target` writes the alias `repos.conf/<overlay>.conf` (setup root);
  `env/<cat>/*.conf`, `package.env/<cat>`, `package.accept_keywords/<cat>` and, for a spec,
  `package.{mask,unmask}/<cat>` (config overlay, else `<root>/etc/portage`);
  `clang/cross/<T>.cfg`; and everything under the sysroot.
- Post-step activation (`select::activate_binutils/compiler/pkgconf`) writes the wrappers and
  `env.d` configs.

## Design

### `--stage N`

1. `StageStep` gets a `level: Level` (`Binutils`, `Compiler`, `Headers`, `Libc`, `Full`,
   `Extra`), set where `toolchain_plan` builds each step. Prerequisites (baselayout, python,
   perl) are `Binutils`; os-headers and kernel headers `Headers`; mixed-model clang steps
   `Full`. LLVM model: wrappers `Binutils`; kernel headers, libc headers and compiler-rt
   `Compiler` (crossdev's headers-in-stage1 rule); libc `Libc`; runtimes `Full`.
2. Levels never decrease along a cross plan, so `--stage N` is a plan prefix and the
   milestone record stays valid. A test asserts it for the gcc, LLVM and mixed plans.
3. `--stage N` keeps the steps with `level <= N`. Extras run only at stage 4; `--ex-pkg`
   with `N < 4` is an error.
4. `--ex-only` keeps only the `Extra` steps and refuses unless the milestones vouch for every
   base step, pointing at `--setup -r`.
5. Both imply `--setup` and keep its `-r`/`-p`/`-a` behaviour, so `--stage 1` then
   `--setup -r` finishes the rest.

Native `toolchain --setup` gets no flag.

### `-C/--clean`

1. Refuse the host CHOST (`reject_same_arch_target`); conflicts with every other action flag.
2. One source for the host-side paths: `host_config_paths(target, globals)`, factored out of
   `cross_env_entries`, `alias_repo_conf_entry` and `clang_cfg_path` and used by both init
   and clean. `env/<cat>/` goes as a whole directory (extras add files to it).
3. Unmerge every installed `cross-<T>/*` in the outer root through em's unmerge path.
4. `select::deactivate(roots, tuple)` removes what the `activate_*` calls wrote; the select
   module owns those paths.
5. Remove `usr/lib/gcc/<T>` and the sysroot `usr/<T>` (config, milestones, saved spec,
   target VDB).
6. `-p` prints the removal list and touches nothing; `-a` confirms first.

## Found on the way

- ✅ An LLVM-model plan returned before the extras loop, so its `--ex-pkg` packages were never
  built (and `--ex-only` there had nothing to run). Both cross paths now append `extra_steps`.
- The milestone record is keyed on the spec without its extras, so naming a new extra keeps
  the base steps done.
- Blocker victims (`unmerge_blocker_victim(s)`) open the VDB and unmerge under `cli.roots()`,
  which `-T` points at the sysroot even when the step merges into the outer root. The classifier
  reads `roots.merge_root()`'s VDB (`load_target_installed_with_cache`), so under
  `use_outer_eroot` the victim is in the outer VDB, `packages_for_unmerge` misses it in the
  sysroot's and the removal is silently skipped. Fix: pass the merge's `roots` into both
  functions (`run_due_unmerges`, the parallel loop and `emerge.rs`'s two batches). Not hit yet.

## Tests

- Plan prefixes per level for gcc, LLVM, mixed; monotonic levels.
- `--ex-only` refuses without complete base milestones; runs only extras with them.
- `--ex-pkg` with `--stage N<4` is an error.
- `host_config_paths` covers every host path `init_target` writes.
- `-C -p` changes nothing; `-C` refuses the host tuple.
- Live, in a fresh crossdev-stages sandbox: `--stage 1`, then `--setup -r` finishes;
  `-C` leaves no `cross-<T>` VDB entries, host config, wrappers or sysroot; a following
  `--setup` succeeds.
